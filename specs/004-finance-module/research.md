# Research: Finance Module

## 1. Needs Clarification / Key Decisions

### Decision 1: Receipt Generation Strategy
**Question**: How should we generate the PDF receipts?
**Options**:
1.  **Client-Side**: Send JSON data to React/React Native, let them generate PDF.
    *   *Pros*: Offloads CPU from server.
    *   *Cons*: Inconsistent receipts across platforms (Web vs Mobile). Harder to audit the exact document generated.
2.  **Server-Side (JasperReports)**: Java standard for heavily formatted reports.
    *   *Pros*: Exact pixel-perfect definition.
    *   *Cons*: Heavy dependency, XML template complexity.
3.  **Server-Side (Thymeleaf + OpenHTMLToPDF)**: Render HTML and convert to PDF.
    *   *Pros*: Easy to style (CSS), lightweight.
    *   *Cons*: Memory intensive for large batches.
**Decision**: **Option 3 (Thymeleaf + OpenHTMLToPDF)**.
*   **Rationale**: We already use Spring. Creating an HTML template for a receipt is easier for developers than Jasper configurations. It ensures the "Official File" is generated by the server for audit.

### Decision 2: Late Fee Calculation (Computed vs Persisted)
**Question**: Should we run a nightly job to add "Late Fee" entries to the ledger, or calculate it on the fly?
**Options**:
1.  **Nightly Batch**: Job runs at 12:00 AM, finds overdue students, inserts `LateFee` record.
    *   *Pros*: Ledger is always static/simple to sum.
    *   *Cons*: Complexity of Quartz/Scheduling. Issues if job fails. State drift.
2.  **Computed on Read**: `getDues()` calculates `max(0, (CurrentDate - DueDate - Grace) * FinePerDay)`.
    *   *Pros*: Always accurate. No batch jobs.
    *   *Cons*: "Total Due" changes every day without a database record update. Harder to generate a static invoice.
**Decision**: **Hybrid Strategy**.
*   **Rationale**: For Phase 1 (MVP), we use **Computed on Read** for the "View Dues" API. When a **Payment** is made, we *crystallize* the Late Fee at that moment into a visible line item if the payment is late. This avoids complex batch jobs while ensuring the paid amount matches the ledger.

### Decision 3: Concurrency & Idempotency
**Question**: How to prevent double charging?
**Strategy**:
1.  **Database Constraint**: Unique Index on `gateway_transaction_id` in `payment_transaction` table.
2.  **Optimistic Locking**: Add `@Version` to `StudentFeeMap` (or the Ledger entity) to prevent two clerks from updating the balance simultaneously.

## 2. Best Practices (Finance)

### Data Types
*   **Money**: ALWAYS use `BigDecimal` in Java and `NUMERIC(19, 2)` in Postgres. NEVER use `Double` or `Float`.
*   **Time**: Use `LocalDateTime` (or `Instant` if multi-timezone, but school is likely local).

### Audit
*   Every modify operation in `FinanceService` must be logged.
*   "Soft Delete" only for Fee Structures. **Hard Delete is PROHIBITED** for Transactions.
